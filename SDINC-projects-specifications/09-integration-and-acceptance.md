# Интеграция и приёмка всего набора

## 1. Порядок реализации за один проход
1. Проверить рабочее дерево, прочитать документацию принятой базы, изучить текущие проекты и демо.
2. Выделить минимальный общий каркас и типы локальных состояний. Не переписывать сайт.
3. Реализовать восемь специализированных экранов по ТЗ. Можно выполнять внутренние шаги последовательно; отдельное согласование после каждого не требуется.
4. Подключить экраны к существующему списку и открытию проекта. Демо оставить девятым.
5. Проверить общую навигацию, фокус, сохранение локальных состояний и отсутствие дублей обработчиков.
6. Выполнить сборку, проверку типов и ограниченный браузерный прогон. Исправить регрессии в разрешённой области.
7. Предоставить итоговый отчёт и визуальные материалы. Без commit/push/deploy.

## 2. Список проектов
Порядок сохраняется:
1. Видео- и аудиоаналитика.
2. Игровые проекты.
3. Открытые разработки.
4. RAG-системы.
5. Собственный чат-бот.
6. Аналитика звонков.
7. Автоматизация коротких видео.
8. Реставрация видео.
9. Демонстрационный проект.

Не стирать демонстрационный образец. Не заменять направления выдуманными брендами. Предпросмотр должен объяснять конкретный экран. Любые изменения списка ограничены его внутренней областью; ранее предложенные 40/60 не считать заранее утверждёнными.

## 3. Основная проверка
Использовать существующие команды из package.json; не предполагать наличие незнакомых скриптов. Проверить сборку и типы фактически. Для итогового браузерного прогона предпочтителен локальный preview актуальной сборки. Не публиковать. Не завершать чужие процессы; остановить только сервер, запущенный для этой задачи.

Контрольный viewport: 1635×938 CSS px, как в предыдущей приёмке. Дополнительно проверить хотя бы один более узкий размер в рамках реально поддерживаемой текущим сайтом desktop-компоновки; назвать точные размеры. Не обещать готовность мобильной версии и не начинать её самостоятельную переработку.

## 4. Матрица по каждому направлению
- Открытие из соответствующего пункта, правильный заголовок и пометка.
- Не менее одного полного уникального сценария из индивидуального ТЗ.
- Мышь, Tab/Shift+Tab, активация нативных элементов.
- Ротор step/confirm без смены глобального режима и двойной активации.
- Возврат к списку с сохранением выбранного проекта и корректным фокусом.
- Повторное открытие с сохранением локального состояния.
- Переход к другому проекту: состояние первого не подменяет состояние второго.
- Скрытые панели не остаются в Tab; нет дублированных идентификаторов и накапливающихся обработчиков.
- Нет обрезки значимых элементов, наложений и перекрытия нижней навигацией.

## 5. Общая регрессия
Один контролируемый маршрут: профиль с нейтральным состоянием → явный выбор SYSTEM → список → все восемь экранов с возвратом → демо со схемой и вкладками → связь, выбор GitHub → профиль → связь → список.

Проверить сохранение явного выбора профиля/контакта, live-card только в профиле, работу демо и отсутствие произвольной смены режима от Tab. Отдельно свежая загрузка: исходные состояния профиля, контакта и локальных демонстраций не конфликтуют. Не выполнять реальные внешние действия ради теста.

Если повторяется одно из ранее описанных dev-наблюдений, применить существующий протокол: сохранить шаги, режим, узел, контакт, activeElement, событие, консоль/trace до предположительных исправлений. Не объявлять старое наблюдение исправленным только потому, что текущий прогон чистый.

## 6. Скриншоты
Нужны корректные изображения списка и всех восьми экранов. Имена должны соответствовать фактическому режиму. Для интерактивных экранов выбрать показательное состояние; для сравнения — 50/50, для RAG — ответ с выделенным источником, для игры — понятное состояние поля.

Указать viewport и использованную сборку. По возможности прикрепить изображения непосредственно в итоговом ответе. Если интерфейс агента этого не позволяет, сообщить ограничение прямо; не утверждать, что пользователь уже увидел локальные файлы. Не включать тестовые артефакты в будущий коммит автоматически.

## 7. Документация и финальный отчёт
Можно добавить отдельный документ реализации экранов и минимальную фактическую запись в существующей документации. Не переписывать принятую базу задним числом и не помечать визуальные изменения как одобренные владельцем.

В отчёте нужны:
- изменённые файлы и краткое назначение;
- таблица восьми экранов: уникальный элемент, выполненный сценарий, итог;
- какие материалы реальны, какие синтетические;
- результаты build/типов/браузера и точные условия;
- ссылки на существующие подтверждённые репозитории, если использованы;
- скриншоты и перечень недостающих реальных материалов;
- известные ограничения и то, что проверить не удалось;
- итоговый git status, без утверждения о чистоте без проверки.

## 8. Когда остановиться досрочно
Только при риске потери данных, конфликте несвязанных чужих изменений, необходимой внешней авторизации/платной операции или невозможности выполнить требования без запрещённой глобальной переработки. Сообщить, что уже сделано и что блокирует продолжение. Не обходить блокер скрытым упрощением и не заявлять незавершённое готовым.
